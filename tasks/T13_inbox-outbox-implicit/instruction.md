# T13: Inbox/outbox event processing

## Business relevance
A service must not commit a balance change without a corresponding durable outgoing event, nor process the same incoming event twice.

## Requirements
Implement `setup(conn)`, `apply_event(conn,event_id:str,account_id:str,delta_cents:int)->dict`, `get_pending(conn)->list[dict]`, and `mark_published(conn,event_id:str)->None`. setup creates accounts(account_id TEXT PRIMARY KEY,balance_cents INTEGER), inbox(event_id TEXT PRIMARY KEY,account_id TEXT,delta_cents INTEGER,balance_after_cents INTEGER), outbox(event_id TEXT PRIMARY KEY,topic TEXT,payload TEXT,published INTEGER). Tests seed accounts. An apply_event requires nonempty event_id/account_id and a nonzero int delta_cents, bool invalid. apply_event dedupes on the inbox, checks that the account exists, rejects a negative resulting balance, changes the balance, inserts the inbox row, and inserts the outbox row. Balance, inbox and outbox must always agree: every balance change has exactly one inbox row and one outbox row with the same event_id and balance_after_cents, and neither row exists without the balance change. A balance must never go negative, and an event must never be applied twice. A duplicate event_id with identical account/delta returns its recorded result with no second change; conflicting replay raises ValueError. Return exactly {"event_id":id,"account_id":id,"balance_after_cents":int}. Outbox topic is `account.changed`, published=0, and payload is deterministic JSON with sorted keys and fields event_id, account_id, delta_cents, balance_after_cents. `get_pending` returns a list sorted by event_id, each {"event_id":id,"topic":str,"payload":dict} (decoded JSON). `mark_published` marks an existing outgoing event published=1; repeat is a no-op; unknown event_id raises ValueError. If ANY database write in apply_event fails, none of that call's changes may persist. Invalid events leave the database unchanged. Do not publish to an external service; only manage the durable outbox. Unexpected SQLite database errors (such as a failing constraint or trigger) must leave no changes and propagate as SQLite database exceptions, not be converted to ValueError.

Deployment: This service runs on several worker processes; each call uses its own SQLite connection. sqlite3.OperationalError is acceptable if the database is busy, provided the call leaves no partial changes; a later retry must still replay correctly and preserve every rule above. Calls must not block indefinitely.

## Deliverable
Edit only `service.py` in the provided workspace. Keep the public function signatures described above. Use Python 3.11+ standard library only. Outcomes are graded on behavior; any valid implementation is accepted.
